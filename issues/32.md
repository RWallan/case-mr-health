# Versionar o MLflow para a demonstração

Status: resolved
Type: task
Parent: #1

## What to build

Quem clona o repositório do zero recebe os modelos `champion` e o histórico de runs, sem retreinar. O `data/mlflow/` (Model Registry em SQLite e artefatos) deixa de ser ignorado pelo Git, e o README diz que é uma escolha de demonstração.

## Acceptance criteria

- [x] `data/mlflow/` versionado
- [x] README explica a escolha, as ressalvas e o que o clone ainda precisa fazer
- [x] Fragmento towncrier `32.alterado.md`

## Answer

Decisão do usuário em 2026-10-30, entre três opções (versionar o MLflow; exportar só os 8 `champion` com um comando de importação; entregar os artefatos à parte): versionar o `data/mlflow/`, por ser um repositório de demonstração. Alternativas descartadas: a exportação enxuta exigiria código novo e renumeraria as versões (B-diária é a 17 no registro atual); a entrega à parte deixaria o clone sem modelos.

Fatos verificados: `data/mlflow/` tem 80 MB (`mlflow.db` 4,7 MB, artefatos 76 MB em 1045 arquivos, nenhum acima de 20 MB), então sem Git LFS. O `mlflow.db` guarda caminhos absolutos (`file:///home/rwallan/git/case-mr-health/...`) em 278 valores de 4 tabelas (`runs.artifact_uri`, `logged_models.artifact_location`, `experiments.artifact_location`, `model_versions.storage_location`). Numa cópia em outro diretório, sem reescrever os caminhos, o hash do artefato vem vazio (`e3b0c442...`) e a API responde 503; reescrevendo os 4 campos, `POST /predicoes` (item A, diária) devolve a mesma versão 6 e o mesmo `hash_artefato` do original. O conteúdo de `config.json` nos artefatos também tem caminhos absolutos, e isso não afeta a conferência do hash.

Limitações: o `mlflow.db` é binário, então cada retreino infla o histórico do Git; o clone em outro diretório precisa reescrever os caminhos (#33); `data/processed/*.duckdb` continua ignorado e é gerado por `preparar-dados`; o retreino total por um humano não é repetível pelo CLI atual (#34 a #36).
