# API de predição individual servindo o champion

Status: resolved
Type: task
Parent: #1
Blocked by: #8, #9

## What to build

Um usuário pede, por HTTP, a previsão de um SKU numa granularidade e recebe quantidade prevista, valor unitário, valor previsto (quantidade × valor unitário), limites de 80% e 95%, versão do modelo, hash e data de geração. A resposta deixa claro que a previsão é da rede.

- Na inicialização, a API carrega um modelo por combinação de SKU e granularidade: a versão `champion` ou uma versão fixada por configuração. O hash do artefato é conferido no carregamento (ADR 0005).
- Nenhuma requisição dispara treino.
- O contrato de entrada tem SKU, granularidade (`diaria` ou `semanal`), data de referência e horizonte opcional. O horizonte é limitado a 14 dias ou 2 semanas, e um pedido acima disso é rejeitado com a justificativa (o horizonte não foi validado empiricamente).
- Erros explícitos para modelo indisponível, granularidade mensal ou não suportada, SKU inexistente, data inválida e campo ausente. Uma requisição semanal nunca usa modelo diário, e vice-versa.
- Cada previsão servida é gravada no histórico de previsões, num DuckDB exclusivo do serviço (ADR 0005), com ID da requisição, SKU, granularidade, datas de geração, referência e alvo, versão, hash, quantidade, valor, intervalos e experimento de origem. O serviço roda com um único worker.
- O código separa rotas, schemas, serviços, carregamento de modelos, persistência e integração com o MLflow.
- Swagger/OpenAPI com descrições, schemas, exemplos e respostas de erro.

## Acceptance criteria

- [x] Testes (Seam 3, TestClient) com modelos pré-registrados num MLflow temporário: seleção do modelo certo, modelo indisponível, mensal rejeitada, horizonte acima do limite rejeitado com justificativa, hash divergente detectado, registro no histórico, nenhum treino disparado

## Answer

**Aceita para integração pelo usuário em 2026-10-30.** `POST /predicoes` serve a previsão da rede por período-alvo, com a versão `champion` ou fixada (`modelos_fixados`) de cada série, sem treinar. Hash conferido no carregamento; série sem versão, com hash divergente ou fora do contrato fica indisponível (503), e a API sobe mesmo assim. Cada período servido vai ao histórico em DuckDB exclusivo, com um único worker.

**Regra da origem fixa (proposta).** Os modelos só preveem a partir do fim do treino. A data de referência é o último período conhecido; os alvos são os `horizonte` seguintes. Passo inicial é a distância entre o último período do treino e a referência, e o último passo não pode passar de 14 dias ou 2 semanas. Na semanal, a referência vai para a segunda-feira.

**Números.** 75 testes em `tests/test_api_predicao.py` passam (9,19 s); lint verde; 9 mutações manuais do código novo derrubam ao menos 1 teste. `uv run poe test` não foi rodado; só a suíte rápida da integração é autorizada pelo plano.

**Achado.** O MLflow reescreve `registered_model_meta` a cada download, conforme a URI. O hash do treino só é reproduzível baixando pela `source` da versão (`models:/m-<id>`), e é o que a API faz, numa cópia. Baixar por `models:/<nome>/<versão>` dá sempre hash diferente.

**Limitações.** A API só atende datas de referência na janela depois do treino, ou seja, em 2021: não prevê o futuro real sem retreino. O valor unitário vem de configuração e é suposição de trabalho. O hash não foi conferido em artefatos reais, e sem o #13 não há `champion`, logo as 8 séries respondem 503 se nada for fixado. A confiança foi removida em #27 (D-020); registro completo em `docs/relatorio/fase5/14.md`.
