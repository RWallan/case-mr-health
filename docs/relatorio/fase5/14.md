**Decisões do coordenador (implementadas, não reabertas):** layout congelado; versão fixada ou `champion`; valor unitário por configuração; origem fixa; lista `periodos`, sem agregar intervalos; `nivel: 'rede'`, `experimento_id` e `run_id`; `nan` vira `null`; erros 404, 503 e 422; histórico exclusivo, um worker; comando `servir`. A confiança saiu da solução pela decisão posterior D-020/#27.

**Regra da origem fixa (decisão proposta).** O modelo foi ajustado até `desenvolvimento_fim` e `prever(n)` devolve os `n` períodos seguintes. A data de referência é o último período conhecido pelo solicitante; os alvos são os `horizonte` períodos depois dela. `passo_inicial` é o número de períodos entre o último período do treino e a referência. O modelo prevê `passo_inicial + horizonte` e só os últimos `horizonte` são servidos. Rejeita-se referência anterior ao último período do treino e último passo acima de `treino.horizonte_maximo` (14 dias, 2 semanas). Na semanal, a referência vai para a segunda-feira da semana, e `desenvolvimento_fim` é um domingo, então o último período do treino é `desenvolvimento_fim - 6`.

**Decisões do agente, a aprovar:**
1. **Comparação semanal por semana, não por dia.** A regra pedia rejeitar referência anterior a `desenvolvimento_fim`. Na semanal, a comparação é feita depois de normalizar: uma quarta-feira da última semana do treino é aceita (passo 0), embora seja anterior ao domingo.
2. **Conferência de série além do nome.** A versão precisa ter as tags de run `sku` e `granularidade` iguais às da série; se não, fica indisponível. Reforça o "semanal nunca usa diário" contra erro de registro.
3. **Prova de contrato no carregamento.** Cada série chama `predict` no horizonte máximo e exige as colunas de 80% e 95%. Versão sem calibração, calibrada para menos passos ou com outros níveis fica indisponível, em vez de falhar na requisição.
4. **Sem previsão sem registro.** Se o histórico falha, a resposta é 503 `historico_indisponivel`. A issue pede que toda previsão servida seja gravada.
5. **Versão fixada não recai no `champion`.** Fixada inexistente ou com hash divergente deixa a série indisponível: quem fixou queria aquela versão.
6. **Ordem da validação:** SKU (404), horizonte sozinho (422), modelo (503), data (422), último passo (422).
7. **Contrato estrito:** campo desconhecido é 422; `data_referencia` só em `AAAA-MM-DD` (o padrão do pydantic aceitaria número como timestamp); `horizonte` só inteiro, e `null` explícito é rejeitado.
8. **`data_geracao` em UTC sem fuso no histórico.** `TIMESTAMPTZ` exige `pytz` para leitura, e ele não está instalado (`ModuleNotFoundError` na leitura). A resposta traz a data com o fuso de `cfg.fuso_horario`.
9. **Chave do histórico** `(id_requisicao, data_alvo)`, com todos os períodos de uma requisição gravados numa só transação. `data_referencia` gravada e respondida é a normalizada; a original não é guardada.
10. **Configuração:** `api_host` (`127.0.0.1`) e `api_port` (`8000`), não pedidos no briefing, para o `servir`.

**Achados inesperados:**
- **O hash do treino só é reproduzível pela `source` da versão.** O MLflow reescreve `registered_model_meta` a cada download (`ModelsArtifactRepository._add_registered_model_meta_file`, `mlflow/store/artifact/models_artifact_repo.py:206` e `:254`): com `model_name: <nome>` em `models:/<nome>/<versão>` e com `null` em `models:/m-<id>`. O treino calcula o hash pela URI `models:/m-<id>`. Consequências: baixar por nome dá sempre hash diferente, e no armazenamento local a escrita acontece no próprio artefato. A API baixa pela `versao.source` para uma cópia temporária com `dst_path`, confere e carrega dessa cópia, sem tocar no armazenamento. Quem mais conferir hash (por exemplo, #13 ou #16) precisa fazer o mesmo. Uma correção melhor seria excluir esse arquivo do hash em `treino.hash_artefato`, mas isso invalida as tags das versões já registradas; não foi feita.
- Alias inexistente responde `INVALID_PARAMETER_VALUE`, não `RESOURCE_DOES_NOT_EXIST`; `resolver_versao` trata os dois como "sem versão".

**Fatos verificados:**
- `uv run pytest tests/test_api_predicao.py`: `75 passed in 9.19s`, com `CASE_MR_HEALTH_INTERVALO_MAX_ORIGENS=5`.
- `uv run poe lint`: `All checks passed!`.
- Mutação manual de 9 pontos (fonte do download, comparação de hash, versão fixada, tags da série, cálculo do passo semanal, fatiamento, limite do último passo, gravação no histórico e `nan`): todas derrubam ao menos 1 teste. Script descartável, fora do repositório.
- Fumaça real de `case-mr-health servir` contra um MLflow vazio em `/tmp`: a API sobe com as 8 séries indisponíveis, `POST /predicoes` responde 503 e 422 com o corpo esperado, `/docs` responde 200.
- Valores unitários conferem com a spec (`issues/1.md`, seção Dados: A=10, B=15, C=20, D=25).

**Limitações:**
- **A API só serve a janela depois do treino.** Com a origem fixa, a data de referência precisa ficar entre o fim do treino e `limite - 1` períodos depois; nas séries atuais isso cai dentro do histórico de 2021. Pedir uma data de hoje é rejeitado. Não há previsão de um futuro real sem retreinar.
- **Mais passos à frente valem para o mesmo modelo, não para dados mais novos.** Com referência depois do treino, os alvos são os passos longos do mesmo ajuste, e as vendas entre o fim do treino e a referência não entram. Os intervalos têm largura constante por passo (ADR 0007).
- **O valor unitário é suposição de trabalho** (glossário) e vem de configuração: a tabela `sku` só existe no `base.duckdb` selado. Mudar o cadastro não muda a API sozinho, e o valor não tem validade no tempo.
- **Na semanal, uma referência no meio da semana trata essa semana como conhecida**, mesmo incompleta, conforme a normalização decidida.
- **Hash não verificado em artefatos reais.** Os testes reproduzem a sequência de `treino._treinar_candidato`, mas `data/mlflow` não foi lido (fora do escopo). Falta confirmar com `servir` depois do `promover` do #13.
- **`champion` não existe até o #13:** sem versões fixadas, as 8 séries respondem 503.
- DuckDB bloqueia o arquivo: com o serviço no ar, outro processo não abre o histórico. Uma conexão serializada por trava, sem teste de carga; um único worker (ADR 0005).
- Os limites são de quantidade, por período; não há limite do valor previsto nem do total de vários períodos.
- `uvicorn` é dependência transitiva de `fastapi[standard]`, sem declaração direta.
- Logs de acesso do uvicorn não passam pelo loguru.

**Contradições sinalizadas (nada foi sobrescrito):**
- A saída da spec inclui `recomendação`; a resposta do #14 não a traz, porque a issue não a lista e ela é da Fase 6.
- A issue fala em "quantidade prevista" como escalar; com horizonte maior que 1 a resposta é uma lista (decisão 5 do coordenador).
- O glossário não define "data de referência". Depois de aprovada a regra, cabe um verbete.
- A regra da origem fixa merece ADR depois de aprovada; não foi escrito por ser proposta.
